# Assumptions

This file tracks assumptions that are useful but not yet validated.

## Product Assumptions

- Retail security and operations teams need help noticing high-risk loss-prevention moments across many live camera feeds.
- A hackathon demo can communicate value through a spatial map, previewable feeds, and one controlled AI-analyzed livestream.
- Human-in-the-loop alert review is safer and more credible than automated decision-making.
- A B2B retail loss-prevention framing is stronger than a public-sector emergency framing for the hackathon.
- A role-based user is clearer than a fixed job title, but the role should remain retail security or store operations.

## Technical Assumptions

- Multimodal models can provide useful descriptions of visual and audio events for a prototype.
- The demo can use looped retail camera videos for non-demo feeds.
- Only the mobile phone livestream needs live AI analysis for the hackathon prototype.
- The alert view can show a short evidence clip from the triggering moment.
- The AI output schema is still undefined.
- The UI experience will be a major part of the judging impact.

## Hackathon Assumptions

- Sentinel is most likely to fit the Wildcard track unless the team emphasizes noisy real-world retail audio for the telli and ai-coustics track.
- Using at least 3 partner technologies should be planned into the architecture from the start.
- Visible partner-technology use should be integrated into the demo narrative, not hidden in implementation details.
